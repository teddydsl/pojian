# 《破茧》架构复核：室内移动反向与后续可扩展性

> 状态：**诊断完成，待决策**（2026-10-31）
> 触发问题：报告「在茧房内走动时，前后移动会出现相反情况」
> **数值复核补充**：[复核与实现路线](STAGE_5A_REVIEW_AND_ROADMAP.md#2-相机诊断的数值复核)。本稿“每帧触发”的距离推导、A／B 机位保证、室内门现状及部分断言需按补充修正；原诊断保留作追溯，不能直接照抄机位参数。
> **实现进度**：R2、比例与受约束机位已进入 [4.1A 验收页](../reviews/stage-4-1a.html)。160 组方向断言与轨道约束检查通过，实际镜头观感仍待用户验收；本文原代码引用为修复前诊断。
> 结论：不是参数没调好，是**相机模型与移动参考系的结构性缺陷**，并且房间几何本身不自洽。同时发现 3 项会随「模型替换 + 新系统」立刻爆发的耦合问题。

## 2. P0-1 移动反向：根因与证据

### 2.1 两套参考系

```js
// 移动：方向只由 state.yaw 决定（stage4-1.js:330-332）
const f = new THREE.Vector3(-Math.sin(state.yaw), 0, -Math.cos(state.yaw));

// 相机：位置由 yaw 算出后，经过两段钳制（stage4-1.js:171-183）
const target = player.position.clone().add(new THREE.Vector3(Math.sin(yaw)*2.45, 2.27, Math.cos(yaw)*2.45));
if (radius > 3.75) { /* 第一段：按坐标半径向圆心压缩 */ }
if (target.distanceTo(player.position) < 3.1) { /* 第二段：改推到「朝向圆心」一侧 */ }
```

正常情况下相机在角色背后，`yaw 前向` 与 `视觉前向` 一致。**但第二段钳制会把相机推到角色「朝向圆心」的那一侧** —— 这正是角色的正前方。于是视觉前方变成 yaw 的相反方向。

### 2.2 为什么第二段几乎总是触发

判定条件是 `相机到角色的距离 < 3.1`，而相机标称距离是 `2.45`。

> **2.45 < 3.1 恒成立** → 只要第一段没把距离拉大到 3.1 以上，这个分支**每一帧都进**。

所以唯一的「正常」情况是玩家正好站在房间正中心（此时 `playerRadius = 0`，回退分支算出的方向恰好与 yaw 相同，掩盖了 bug）。玩家一离开中心点就开始偏转。

### 2.3 数值验证（实测脚本复刻原函数，每 15° 采样）

| 玩家位置 | 半径 | 现状最差角度偏差 | 判定 |
|---|---|---|---|
| (0, 0) 正中心 | 0.00 | 0° | 正常（假象） |
| (2.0, 0) 走到一半 | 2.00 | **180°** | 完全相反 |
| (-2.65, -0.55) 站在数据面板前 | 2.71 | **177°** | 完全相反 |
| (3.2, 1.4) | 3.49 | **174°** | 完全相反 |
| (0, -3.8) 站在出口 | 3.80 | **180°** | 完全相反 |
| (4.3, 0) 贴墙 | 4.30 | **180°** | 完全相反 |

→ 与「有时前后相反、有时斜着走」的观察完全吻合：**偏差角度随位置与朝向连续变化**（0°~180°），所以表现为时对时错、时正时斜。

### 2.4 修复原则（不接受「把阈值改小」这种补丁）

只要移动方向继续取自 `yaw`、相机位置继续被独立钳制，两者就还会分叉。**必须让移动方向从相机实际朝向反算**：

```js
// 每帧：相机朝向在 XZ 平面的投影即为「前」
const forward = new THREE.Vector3().subVectors(player.position, camera.position).setY(0).normalize();
```

这样「W 朝远离相机的方向走」在数学上恒成立，与相机怎么被钳制无关。**这是唯一不会复发的写法。**

## 3. P0-2 房间几何不自洽

现有四个半径：

| 量 | 值 | 来源 |
|---|---|---|
| 穹顶内半径 | 4.78（球，y 压扁 .86） | `stage4-art.js:322` |
| 地面半径 | 4.76 | `stage4-art.js:324` |
| 玩家活动上限 | **4.32** | `stage4-1.js:343` |
| 相机允许半径 | **3.75** | `stage4-1.js:174` |

「角色身后跟随 + 永远留在穹顶内 + 不贴近角色」要同时满足：

```
玩家半径(4.32) + 最小相机距离(约 2.4) = 6.7  >  相机允许半径(3.75)
```

**不等式无解。** 实测：贴墙时沿 yaw 方向求交，相机只能在 0.14m 处，若强制最小 1.1m 则相机穿墙到半径 5.14。这就是为什么原代码改用「把相机推到圆心侧」——那是绕开几何矛盾的做法，代价就是 P0-1。

### 3.1 三种可行方案

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 环绕机位** | 相机固定在「绕房间中心半径 3.4、高 3.2」的环上，`yaw` 只控方位角，`lookAt` 角色；不跟随平移 | 永不穿墙、永不与角色重叠、室内细节看得全 | 镜头不再贴身，沉浸感弱于跟随；角色走到镜头同侧时会偏大 |
| **B 高俯视 diorama** | 相机半径 2.2、高 4.6、俯角约 60°，绕中心旋转 | 方向感最稳；契合「微缩针毡」美术调性 | 穹顶顶面成主视觉，室内道具需按俯视重排 |
| **C 跟随+抬高** | 距离按射线求交缩短，缩短时抬高相机并加大俯角 | 保留跟随手感 | 贴墙时仍会被压到很近（t≈1.1m），角色占满画面；实现最复杂 |

三者都需要配套 **P0-1 的移动参考系修复**，否则一样会错方向。

## 4. P0-3 坐标锚点散布（换模型的必崩点）

「P0-1 之外，模型一换就出问题」的具体位置：

| # | 锚点 | 位置 | 换什么会崩 |
|---|---|---|---|
| 1 | `trees` 15 棵程序化树坐标 | `stage4-art.js:133` | 换成 stylized-tree 树模型 |
| 2 | `forestObstacles` 树碰撞半径 | `stage4-art.js:136` | 同上（半径 .55 按旧树算） |
| 3 | 4 枚背景挂置茧房的挂点 | `stage4-art.js:311-318` | 同上（挂点坐标与树位重复维护，改一处漏一处） |
| 4 | `huts` 三间茧房的 `x / z / doorZ` | `stage4-art.js:219` | 换茧房门、换门前场地 |
| 5 | `ownDoorTarget` (0,0,7.75) | `stage4-art.js:303` | 同上 |
| 6 | `panelApproach` (-1.5,0,-.55) | `stage4-art.js:438` | 换室内数据面板视图 |
| 7 | `exitTarget` (0,0,-3.8) | `stage4-1.js:77` | 换室内门模型 |
| 8 | `furnitureColliders` 三房间家具碰撞 | `stage4-1.js:76` | 换室内家具 |
| 9 | 森林边界 `x[-15,15] z[-16,11.2]` | `stage4-1.js:336` | 换树、扩地图 |

**结论**：需要一份 `layout.js` 作为唯一坐标事实源，美术层与逻辑层都从这里读。否则「模型替换」与「交互功能」不能并行 —— 每换一次模型都要手工回归 10 处。

此外：室内当前在 `importedEgg` 分支下**根本没有创建门扇**（`stage4-art.js:270` 的 `if (!importedEgg)`），`door` 组是空的。也就是说「室内换门」不是替换，而是**新增**——那时 `exitTarget` 必须与新门的实际位置对齐。

### 6.1 三档重构力度

## 7. 修复后应新增的自动断言

1. 室内任意位置（中心 / 中段 / 贴墙 / 面板前 / 出口）× 8 个朝向，`yaw 前向` 与 `相机→角色` 夹角必须 < 5°
2. 室内相机位置半径恒 ≤ 穹顶半径 − 0.3
3. 相机与角色水平距离恒 ≥ 1.0
4. 森林与室内两套相机切换后，移动方向立即正确（不残留上一模式的前向）
5. `layout.js` 中每个锚点被 `art-*` 与逻辑层同时引用（单一来源）
